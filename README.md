# 波兰铁路游戏知识库（文档站）

[wiki.plrail.com](https://wiki.plrail.com) 的文档源码。基于 Docusaurus 3 的**纯静态站**，
内容按游戏拆成 5 个互相独立的文档实例：SimRail · Maszyna · TD2 · ISDR · TPF2。

改内容 → 提交 PR → 合并进 `main` → 流水线自动构建并发布。**贡献者不需要接触服务器与部署凭据。**

## 贡献方式

1. Fork 本仓库并克隆到本地（首次 clone 前先执行 `git lfs install`，见「环境准备」）。
2. 在目标游戏的目录里改内容：正文写进 `docs/<游戏>/`，配图放进 `static/img/<游戏>/`。
3. 本地预览 + 跑一遍「提交前检查」，确认无误后提 PR，并在描述里**说明改了什么、怎么验证的**。

不确定内容该归哪个游戏、哪一章，或者要新增一个游戏，先看 [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 环境准备

需要 Node.js >= 18（CI 使用 20）。

```bash
git lfs install   # 必须先执行：图片等二进制走 Git LFS，漏装会把原文件直接写进 Git 历史
npm install
npm run start     # http://localhost:3000/
```

图片等二进制由 Git LFS 跟踪，规则写在 `.gitattributes`（`*.png` `*.jpg` `*.gif` `*.webp` `*.mp4` `*.pdf` 等）。
自检：

```bash
git lfs ls-files                                 # 被 LFS 跟踪的文件
git check-attr filter -- static/img/logo.png     # 应输出 filter: lfs
```

## 常用命令

| 命令 | 作用 |
| --- | --- |
| `npm install` | 安装依赖 |
| `npm run start` | 开发预览，默认 <http://localhost:3000/>；端口被占用时 `npm run start -- --port 3001` |
| `npm run build` | 生产构建，产物输出到 `build/` |
| `npm run serve` | 本地验证生产构建 |
| `npm run check-slug` | 校验同一实例内 URL 是否重复（PR 门禁）；`INSTANCES="simrail" npm run check-slug` 只查一个实例 |
| `npm run search:index` | 重建 Meilisearch 索引（仅站点已接入 Meilisearch 时才需要） |

**不要在 `npm run start` 运行时执行 `npm run build`。** 两者共用 `.docusaurus/` 目录，并发执行会把
开发服务器的内容注册表写成生产态，所有文档页都会报 `Cannot read properties of undefined (reading 'id')`。
真出现了就停掉 dev、删掉 `.docusaurus/` 再重启。

## 目录说明

| 路径 | 用途 |
| --- | --- |
| `docs/<游戏>/` | 文档源文件，一个游戏一个目录：`simrail` `maszyna` `td2` `isdr` `tpf2` |
| `sidebars/<游戏>.js` | 该游戏的侧边栏，配置为 `autogenerated` |
| `static/img/<游戏>/` | 文档配图，按游戏分目录 |
| `static/file/<游戏>/` | 供读者下载的附件（PDF 等） |
| `src/` | 站点前端代码：首页、导航组件、主题覆写、样式 |
| `i18n/en/` | 英文译文，**当前不参与构建**（原因与恢复方式见 [ARCHITECTURE.md](./ARCHITECTURE.md)） |
| `scripts/` | 维护脚本：slug 检查、搜索索引、FTP 部署 |
| `docusaurus.config.js` | 站点、实例、搜索的配置入口 |

新增一篇文档：直接在 `docs/<游戏>/` 下建 `.md` 即可。侧边栏是自动生成的，新文件会自己出现，
顺序由 frontmatter 的 `sidebar_position` 控制。

## 文档写作规范

### frontmatter

每篇文档开头都必须有 frontmatter（`---` 包起来的 YAML）。现有 76 篇文档统一使用下面 6 个字段：

```md
---
sidebar_position: 2
title: 机车车辆
description: SimRail 机车车辆一览
keywords: [SimRail, 机车, 车辆]
tags: [SimRail, 车辆]
slug: /vehicles/rolling-stock
---
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 页面标题。浏览器标签、搜索结果、页面顶部的标题都用它 |
| `description` | 是 | 一句话摘要。搜索结果与分享预览显示的就是这句 |
| `sidebar_position` | 是 | 同级条目在侧边栏中的排序，数字、从 1 开始；不写会排到最后且顺序不稳定 |
| `slug` | 是 | 该篇在**实例内**的绝对路径，见下 |
| `keywords` | 建议 | 关键词数组，只给搜索引擎看，不显示在页面上 |
| `tags` | 建议 | 标签数组，用于站内聚类；各游戏首页（`intro.md`）可以省略 |

YAML 写法注意：

- 字段名必须小写，`key: value` 的冒号后面要有一个空格。
- 值里含 `:` `#` `[` `]` 等字符时用引号包起来，例如 `description: "ETCS：欧洲列车控制系统"`。
- 数组两种写法都行：`keywords: [SimRail, ETCS]`，或每行一个 `- SimRail`。
- **拼错字段名不会有任何提示**：`sidebar_positions: 2` 这种既不会报错也不会警告，只是静默失效，
  所以改完 frontmatter 一定要回本地预览确认效果。反过来，`draft: true` 和 `unlisted: true` 同时写
  会让构建直接失败（报 `Can't be draft and unlisted at the same time.`）。

#### slug 怎么写

`slug` 是**实例内**的绝对路径，与目录结构保持一致；最终 URL = 实例路由前缀 + `slug`：

| 文件 | `slug` | 最终 URL |
| --- | --- | --- |
| `docs/simrail/intro.md` | `/` | `https://wiki.plrail.com/simrail/` |
| `docs/simrail/general/etcs.md` | `/general/etcs` | `https://wiki.plrail.com/simrail/general/etcs` |
| `docs/simrail/station/station_info/dorota.md` | `/station/station_info/dorota` | `https://wiki.plrail.com/simrail/station/station_info/dorota` |

每个实例的首页固定是 `intro.md` + `slug: /`。**同一个实例内 slug 不能重复**，判断与修法见「URL 与 slug」。

#### 正文标题

frontmatter 之后习惯再写一次一级标题，文字与 `title` 相同：

```md
---
title: 机车车辆
slug: /vehicles/rolling-stock
---

# 机车车辆

正文从 `##` 开始分层。
```

正文开头这一行会被 Docusaurus 拿去当页面标题，**不会**和 `title` 一起渲染成两个 `h1`（每页只有一个 `h1`）。

#### 按需使用的可选字段

以下字段 Docusaurus 都支持、**本站目前没用**，需要时直接加：

| 字段 | 用途 |
| --- | --- |
| `sidebar_label` | 侧边栏里的显示名（与 `title` 不一致时用） |
| `sidebar_class_name` | 给该侧边栏条目加类名，配合自定义样式 |
| `hide_title` | 隐藏页面顶部标题 |
| `hide_table_of_contents` | 隐藏右侧目录 |
| `toc_min_heading_level` / `toc_max_heading_level` | 右侧目录收录的标题层级，取值 2~6（默认 2~3） |
| `draft` | 草稿：开发预览可见，生产构建跳过 |
| `unlisted` | 不进侧边栏与搜索索引，但 URL 仍可访问（**与 `draft` 互斥**） |
| `pagination_label` / `pagination_next` / `pagination_prev` | 自定义「上一篇 / 下一篇」的文案与跳转目标 |
| `image` | 社交分享时的预览图（默认用站点图） |
| `last_update` | 覆盖页面底部「最后更新」的时间与作者 |
| `custom_edit_url` | 覆盖「编辑此页」的链接 |
| `displayed_sidebar` | 手动指定该篇属于哪个侧边栏（本站每个实例一个侧边栏，一般不需要） |
| `parse_number_prefixes` | 允许用 `02-faq.md` 这类数字前缀控制顺序（本站用 `sidebar_position`，不需要） |

### 目录分组：`_category_.json`

frontmatter 管的是**单篇文档**；**目录**的分组名、组间顺序和目录索引页由该目录下的 `_category_.json` 管
（本站 `docs/simrail/` 下有 3 处）：

```json
{
  "label": "通用信息",
  "position": 2,
  "collapsed": true,
  "link": {
    "type": "generated-index",
    "description": "SimRail 通用知识",
    "slug": "/general"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `label` | 侧边栏里这个分组显示的名字 |
| `position` | 分组之间的排序 |
| `collapsed` | 初始是否收起 |
| `link.type` | `generated-index` = 自动生成一个「本目录下所有文档」的索引页 |
| `link.slug` | 索引页地址，同样不能和文档 slug 撞车（但它**不在** `check-slug` 的检查范围内，改的时候自己留意） |

### 标题与锚点

标题后可以加 `{#anchor}` 固定锚点，避免以后改标题导致站内链接失效：

```md
## 环境要求 {#requirements}
```

### 折叠面板

折叠面板用 HTML 的 `<details>` / `<summary>`。Docusaurus 主题自带这套映射
（`@theme/MDXComponents` 里 `details` → `@theme/Details`），会渲染成带样式的信息块，
**不需要引入任何组件，也不需要额外注册**。站内 68 篇文档都是这么写的：

```md
<details>
<summary>基本</summary>

![多罗塔站调度面板（基本视图）](/img/simrail/station/station_info/dorota/panel-basic.webp)

</details>
```

写法要求：

- `<details>`、`<summary>`、`</details>` **各自独占一行**；`</summary>` 之后、`</details>` 之前各留一个空行，
  中间的内容才会按 Markdown 解析 —— 图片、列表、表格、代码块都可以放。
- 默认是收起的。要默认展开就给 `<details>` 加 `open`：`<details open>`。
- `<summary>` 必须是 `<details>` 的**直接子元素**：主题靠它把标题栏摘出来单独渲染。
- `<summary>` 里写一句能概括内容的话，不要只写「展开」「更多」。

### MDX 注意事项

- **标签要独占一行，且和内容之间留空行**，否则整段会被当成普通文本。
- **内容不要缩进**。MDX / Markdown 里 4 个空格缩进会被解析成代码块。
- 正文里的 `{` `}` 会被当作 JSX 表达式求值，需要写成 `\{` 或用反引号包起来。
- 在正文里提到标签时要用反引号（`` `<details>` ``），直接写会被当成真实标签去渲染。
- 表格单元格里同样要用反引号包裹 `<details` 这类内容。

### 图片与附件

- 配图放 `static/img/<游戏>/<分类>/`，用**绝对路径**引用，不要写相对路径：

  ```md
  ![ETCS 级别 0 的 DMI 显示](/img/simrail/general/etcs/level-0.png)
  ```

- 每张图都要写**有意义的 `alt`**（上面方括号里的文字），它读屏软件唯一的描述来源。
- 供读者下载的附件（PDF 等）放 `static/file/<游戏>/`。
- 截图优先用 `.webp`，并尽量控制单张体积：站点产物约 533 MB，其中 497 MB 是配图。
- 图片走 Git LFS，提交前确认本机跑过 `git lfs install`。

### URL 与 slug

每篇文档的最终 URL（permalink）必须在**同一个实例内唯一**。两条相同的路由会让后加载的那篇覆盖先加载的，
表现为页面丢失、导航随机跳错。注意 `npm run build` 对这种情况**只打 WARNING（`Duplicate routes found!`）、
不会让构建失败**，所以单独设了一道门禁：

```bash
npm run check-slug     # 有重复就退出码 1
```

常见触发原因：文件名数字前缀（`02-faq.md` 与 `faq.md` 撞车）、`index` / `README` / 与目录同名的首页文件、
显式写了重复的 `slug`。修法是给其中一篇加唯一 slug，或合并 / 删除重复文档：

```md
---
slug: /faq/install
---
```

检查脚本本身怎么复算路由，见 [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 提交前检查

- [ ] 文件放在了正确的游戏目录，侧边栏顺序符合预期
- [ ] 配图放在 `static/img/<游戏>/`，用绝对路径引用，`alt` 有意义
- [ ] 站内链接能点开，没有指向已删除的页面
- [ ] 本地预览里标题、列表、图片、`<details>` 折叠面板都正常
- [ ] 下面三条命令都通过

```bash
git diff --check        # 多余空白
npm run check-slug
npm run build
```

`npm run build` 成功**只代表源码能生成站点**，不代表内容正确，也不代表已经上线。

## 发布

| 工作流 | 触发 | 作用 |
| --- | --- | --- |
| `.forgejo/workflows/pr-check.yml` | PR 到 `main`（opened / synchronize / reopened） | 跑 `check-slug`，失败则 PR 检查不通过、不能合并 |
